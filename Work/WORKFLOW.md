## 完整工作流

### 阶段一：创意 → 需求文档（Plan）

1. **提出想法**（Magix / 任何人）
2. **清音评估并输出需求文档** → 放入 `Work\Plan\Kiyone\`
3. **全员评估**：琉璃、凛月、夕奏读取 `Work\Plan\Kiyone\` 中的需求文档
   - 各自从自己专业角度评估可行性
   - 可进行多轮讨论拉齐
4. **最终版交给清音修订**，定稿后由清音移入她的 Doing 区

### 阶段二：排期 → 执行（Doing）

5. **清音将定稿需求移入** `Work\Doing\Kiyone\`
6. **各角色读取 Doing 区需求文档**，在自己的 Plan 区输出专业方案：
   - **琉璃（后端）** → 在 `Work\Plan\Liuli\` 输出后端方案文档
   - **凛月（前端）** → 在 `Work\Plan\Ritsu\` 输出前端方案文档
   - **夕奏（测试）** → 在 `Work\Plan\Kanade\` 输出测试方案文档
7. **多轮拉齐**方案，达成共识后：
   - 各人将方案移入自己的 Doing 区 → `Work\Doing\Liuli\` 等
   - 开始编码/实施

### 阶段三：完成 → 归档（Done）

8. **夕奏完成测试**，确认通过
9. **各人将自己的方案文档移入 Done 区归档：**
   - 琉璃 → `Work\Done\Liuli\`
   - 凛月 → `Work\Done\Ritsu\`
   - 夕奏 → `Work\Done\Kanade\`
10. **清音将需求文档移入** `Work\Done\Kiyone\`

## 琉璃的工作流程（后端工程师）

### 我的角色职责
- **输入端**：读取 `Work\Doing\Kiyone\` 中清音的定稿需求文档
- **输出端**：在 `Work\Plan\Liuli\` 撰写后端架构方案
- **执行端**：`Work\Doing\Liuli\` 存放正在开发的方案
- **归档端**：`Work\Done\Liuli\` 存放已完成归档的方案

### 我的方案文档标准
后端方案文档应包含：
| 要素 | 说明 |
|------|------|
| 背景与目标 | 这个需求要解决什么问题 |
| 数据模型 | Model 设计、字段说明、索引策略 |
| API 接口 | 路由、方法、请求体、响应体、权限 |
| 业务逻辑 | 核心流程、状态机、异常处理 |
| 安全考量 | 权限校验、数据脱敏、防注入 |
| 与前端约定 | 约定字段名、格式、分页策略 |
| 变更记录 | 版本号、日期、变更人、变更说明 |

### 我的工作流步骤
1. 清音将需求定稿移入 **Doing/Kiyone** → 我读取
2. 我在 **Plan/Liuli** 输出方案文档
3. 与凛月、夕奏、清音拉齐方案
4. 方案定稿 → 移入 **Doing/Liuli** → 开始开发
5. 开发完成 → 夕奏测试通过 → 移入 **Done/Liuli**

## 通用原则

- **文档为王**：一切以文档驱动，方案文档要详细、易懂、便于拉齐
- **各负责自己的文件夹**：每人只管理自己姓名下的子目录
- **移动由本人操作**：从 Plan→Doing→Done 的每一步由文件持有者自己操作
- **未经拉齐不下手**：方案必须经过团队评估和拉齐才能进入 Doing 阶段
- **版本留痕**：方案文档保留版本号和变更记录，便于回溯
