## 1. 背景与目标

### 概述

b1.7 第一轮优化（同步 401 修复、排行榜重写、BP 白屏修复等）已于 2026-05-02 完成并落地。经测试和生产验证，仍有以下问题需在第二轮修复。

### 目标

修复所有已知数据与交互问题，优化排行榜体验，确保排行榜/成绩详情数据正确性、模式判断精准、UI 交互合理。

## 2. 问题列表与功能描述

### 2.1 [P0] 同步仍 401 — `api/users/sync-osu` 未修复

**现象**: `POST /api/users/sync-osu` 仍然返回 401（单次报错四次，推测四模式各自失败）。

**说明**: 第一轮报告的同步 401 修复了未登录拦截等边界情况，但实际用户同步请求仍然失败。

**修复要求**:
- 琉璃深入排查根因（可能是 token refresh 流程、scope 未生效、或 middleware 拦截）
- 修复后需用真实 osu 账号验证全流程同步
- 各模式独立返回结果（同第一轮约定）

---

### 2.2 [P1] 成绩详情 — Aim/Speed 仅限 standard 模式

**现象**: 查看详细成绩时，Aim 和 Speed 两个指标在所有模式（taiko/catch/mania）下都显示。

**问题**: Aim 和 Speed 是 **standard 模式特有的评价标准**，其他模式不应展示。

**修复要求**:
- 前端根据当前模式判断是否展示 Aim/Speed
  - standard → 显示 Aim / Speed
  - taiko / catch / mania → **隐藏** Aim / Speed
- 后端如返回了四个模式的 Aim/Speed 值也不用管，前端按模式过滤显示即可

---

### 2.3 [P1] 成绩详情 — Standard 的 Aim/Speed 也是 0.00

**现象**: 即使在 standard 模式下，Aim 和 Speed 也显示为 0.00。

**问题**: 后端返回的数据中 Aim/Speed 字段值为 0，说明同步/存储的数据有问题。

**修复要求**:
- 琉璃排查同步逻辑：`GET /users/{user}/scores/best` 返回的 Score 对象中是否包含 `statistics.aim` / `statistics.speed` 字段
- 检查 OsuScore Model 中 Aim/Speed 的映射和存储逻辑
- 如 osu! API 不直接返回，需要从 PP 相关字段中解析

---

### 2.4 [P1] 成绩详情 — OD（Overall Difficulty）始终为 0

**现象**: 所有谱面的 OD 字段返回 0。

**问题**: 同步或查询时 beatmap 的 OD 数据未正确获取/存储。

**修复要求**:
- 琉璃确认 osu! API `GET /beatmaps/{beatmap}` 响应中 `accuracy`（即 OD）字段是否被正确读取
- 检查 OsuScore Model 中 OD 的映射字段
- 确保同步时随 beatmap 信息一起写入

---

### 2.5 [P0] 最近游玩/通过缺少非 Ranked 谱面记录

**现象**: 最近游玩（Recent）和最近通过（Pass）中仍有非 Ranked 谱面（Loved/Qualified/Pending/WIP/Graveyard）的记录缺失。

**问题**: 后端 API 在返回这些列表时可能仍按 `status='ranked'` 过滤，或同步时跳过了非 Ranked 谱面的成绩。

**修复要求**:
- 琉璃确认后端查询逻辑：`pass` / `recent` / `todaybest` 的查询是否 filter 了 beatmapStatus
- 理论上 osu! API 会返回所有谱面状态的数据，不应有过滤
- 如果数据库中没有非 Ranked 谱面的记录，需确认同步引擎是否跳过了它们

---

### 2.6 [P1] 排行榜去除模式筛选框（S|T|C|M）

**现象**: 排行榜页面目前有 standard / taiko / catch / mania 四个模式 Tab。

**问题**: BeatmapID（BID）本身是唯一的，一个 BID 对应一张谱面，谱面自带一个 mode。所以模式的筛选是多余的。用户如果选错模式会看不到排行榜，造成困惑。

**修复要求**:
- **去除排行榜的模式 Tab/筛选框**
- 排行榜根据输入的 BID 自动确定该谱面的 mode（后端返回 `beatmap.mode` 字段）
- 用户只需要输入 BID，不需要关心它是哪个模式的
- 如果后端返回的谱面信息包含 mode 字段，前端直接使用

**例外**: 用户个人 BP 查看等按用户维度的页面仍保留模式 Tab（用户自己有四模式的 BP），仅按谱面的排行榜去除。

---

### 2.7 [P2] 排行榜去除 Mod 选择框

**现象**: 排行榜页面上有 Mod 筛选（NM/HD/HR/DT 等）。

**问题**: Peppy（osu! 官方）不允许第三方网站按 Mod 过滤排行榜，这是赞助者（Supporter）专属功能。

**修复要求**:
- 去除排行榜上的 Mod 筛选框/选择器
- 排行榜默认显示全部 Mod 混合的排名

---

### 2.8 [P1] 判定详情直接展示（不折叠）

**现象**: 判定详情（300/100/50/Miss 等）当前需要点击展开/下拉才可见。

**修复要求**:
- 判定详情直接在排行榜条目中展示，不折叠
- 桌面端始终保持可见
- 移动端适配可暂时不考虑

---

### 2.9 [P2] 四模式判定名称需灵活展示

**现象**: 不同 osu 模式的判定有不同的命名系统：

| 模式 | 判定名称（从好到差） |
|------|---------------------|
| standard | GREAT / OK / MEH / MISS |
| taiko | GREAT / OK / MISS |
| catch | GREAT / L DRP / S DRP MISS / MISS |
| mania | PERFECT / GREAT / GOOD / OK / MEH / MISS |

**修复要求**:
- 前端根据 `mode` 字段动态选择对应的判定名称和数量
- 不在 UI 中硬编码 standard 的判定结构
- 如后端返回 `countGreat` / `countOk` / `countMeh` / `countMiss` 等通用字段，前端按 mode 映射显示名称
- 如后端按模式返回不同字段名，需对齐命名

**建议方案**:

后端统一使用通用字段名：
```
countGreat, countOk, countMeh, countMiss, countPerf, countLDrp, countSDrpMiss
```
前端按 mode 取舍显示哪些：

| 模式 | 显示字段 |
|------|---------|
| standard | countGreat / countOk / countMeh / countMiss |
| taiko | countGreat / countOk / countMiss |
| catch | countGreat / countLDrp / countSDrpMiss / countMiss |
| mania | countPerf / countGreat / countGood / countOk / countMeh / countMiss |

---

### 2.10 [P1] 排行榜分数始终为 0

**现象**: 排行榜条目中分数字段始终显示 0。

**问题**: 后端返回的 `score` 字段值不对。可能是总分字段映射错误（`total_score` vs `score` vs `legacy_total_score`）。

**修复要求**:
- 琉璃确认 OsuScore 存储及排行榜 API 返回的 `score` 字段是否正确映射
- 参考 osu! API v2 Score 对象：`total_score`（lazer standardised score）或 `legacy_total_score`（stable 旧分制）
- b1.7 我们固定走 stable（`legacy=1`），应使用 `legacy_total_score` 或 `score` 字段

---

### 2.11 [P1] 排行榜排名格式 — `#4` / `#20` 而非 `#S`

**现象**: 排行榜排名显示为 `#S` 等评级符号。

**问题**: 排名序号应该用数字格式，评级（S/A/B/C/D）应放在分数前面或另一位置。

**修复要求**:
- 排名序号格式改为 `#1` / `#4` / `#20` / `#100`
- 前 3 名特殊样式保留（金牌/银牌/铜牌 或 🥇🥈🥉）
- 评级（Grade: S/A/B/C/D）移到分数前面或分数右侧

---

### 2.12 [P1] 排行榜 — 未上榜时显示用户自己的成绩

**现象**: 当前只有上榜用户才显示记录，未上榜用户什么也看不到。

**修复要求**:
- 即使当前用户未进入前 N 名排行榜，只要用户在**该谱面有成绩记录**，就应在页面上展示
- **UI 布局位置确认（凛月建议）**: userScore 条目放在 **BeatmapHeader 下方、排行榜列表上方**，固定展示（sticky），不随列表滚动：

  ```
  BeatmapHeader       ← 顶部谱面信息卡
  ─────────────────
  你的成绩             ← userScore 固定区域（有成绩则显示）
  ─────────────────
  Leaderboard List    ← 正常排行榜条目
  ```

- 展示格式同排行榜条目，包含完整判定/分数/Mod
- 加标注「你的成绩」以区别于榜单
- 后端需返回 `userScore` 字段（如果用户有成绩的话）

#### 后端响应补充

```json
{
  "currentUserRank": { "rank": null, "score": ... } | null,
  "userScore": {
    "score": 7654321,
    "accuracy": 96.78,
    "count300": ..., "count100": ..., "countMiss": ...,
    "mods": ["DT"],
    "grade": "A",
    "rank": null,
    "isOnLeaderboard": false
  } | null
}
```

### 2.13 [P3] 回到顶部按钮

**现象**: 排行榜数据量可能很大，页面滚动后不方便回到顶部。

**修复要求**:
- 页面右下角固定一个「回到顶部」按钮
- 仅在页面滚动超过一屏后出现
- 点击后平滑滚动到页面顶部

---

### 2.14 [P1] 排行榜顶部显示谱面详细信息

**现象**: 搜索 BID 后当前页面没有展示该谱面的完整信息。

**修复要求**:
- 搜索 BID → 获取排行榜数据后，在页面最顶部展示该谱面的详细信息卡片
- 包含：封面图、曲名、艺术家、难度名、星级、BPM、时长、OD、CS、AR、状态标签、模式标签
- 信息来源于排行榜接口返回的 `beatmap` 对象

---

### 2.15 [P2] 搜索 BID 后搜索栏不隐藏

**现象**: 当前排行榜搜索栏在搜索完成后可能会收起/隐藏。

**修复要求**:
- 搜索完成后搜索栏保持可见
- 方便用户切换 BID 重新搜索

```

- OD（overall_difficulty）不应为 0
- Aim / Speed 值正确返回
```

### 4.4 判定字段命名对齐

经过讨论，后端统一使用以下通用字段名：

| 字段 | 类型 | 说明 |
|:----:|:----:|:------|
| `countGreat` | Number | 所有模式都有 |
| `countOk` | Number | standard/taiko/mania 有 |
| `countMeh` | Number | standard/mania 有 |
| `countMiss` | Number | 所有模式都有 |
| `countPerf` | Number | mania 专属（PERFECT） |
| `countLDrp` | Number | catch 专属（Large Droplet） |
| `countSDrpMiss` | Number | catch 专属（Small Droplet Miss） |

当前 `count300/count100/count50/countMiss` 可作为 `countGreat/countOk/countMeh/countMiss` 的同义映射：
- `count300` → `countGreat`
- `count100` → `countOk`
- `count50` → `countMeh`

> **建议**: 排行榜响应中同时保留两组字段，前端逐步迁移，避免凛月现有组件断联。

## 5. 前端技术约束
